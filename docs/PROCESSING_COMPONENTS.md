# Компоненты обработки декларации Forma

Проверка от 21 ноября 2026 года. Для PDF стоит расширить использование уже установленного pdfplumber. Перевод всего потока на локальный Unstructured `hi_res` не дал выигрыша в точности товарных строк. На уровне конечного XML наибольшая видимая потеря в проверенном комплекте — графа 44. Для дальнейшего сравнения компонентов приоритетны реестр документов и распознавание повёрнутых сканов.

## Сравнение парсеров

Прямая выборка состояла из шести PDF, семи страниц и двух комплектов. В примере 3 это коммерческий инвойс IV-14 и его упаковочный лист. В примере 5 — русский счёт, упаковочный лист, скан спецификации и обе страницы повёрнутой банковской ведомости. Для контроля открыты изображения исходных страниц. Проверка изменения действующего парсера отдельно охватила PDF всех пяти комплектов.

Испытан локальный Python-пакет Unstructured 0.27.37 с unstructured-inference 1.6.17, YOLOX, Microsoft Table Transformer, Tesseract `rus+eng`, `strategy="hi_res"` и `infer_table_structure=True`. Тест использовал публичные веса локально. Облачный Unstructured не участвовал. Для Forma использованы результаты штатного извлечения, совпадающие по SHA-256 с исходными PDF. На сканах это включает кэш OCR профиля DeepSeek Flash. [Unstructured](https://github.com/Unstructured-IO/unstructured) · [Извлечение таблиц](https://docs.unstructured.io/open-source/how-to/text-as-html)

| Проверка | Действующая Forma | Локальный Unstructured |
|---|---|---|
| Инвойс IV-14, 36 строк | В тексте 36 из 36 строк сохранили артикул, количество, цену и сумму. Модель вернула 36 точных строк | Проверка привычного формата строки не смогла собрать ни одной из текста элементов или строк HTML. Из совокупности текста и HTML модель восстановила все 36 |
| Упаковочный лист IV-14, 34 строки | В тексте и после модели 34 из 34 строк сохранили артикул, количество, общий вес нетто и брутто строки | Артикулы и значения распределились по элементам. По тексту и HTML модель восстановила все 34 строки |
| Русский счёт и упаковочный лист | Счёт прочитан построчно. В упаковочном листе количество оказалось на следующей строке. Чтение по границам ячеек возвращает количество между единицей измерения и примечанием | В счёте распознаны две таблицы. В упаковочном листе ни одного элемента Table |

| Повёрнутая банковская ведомость | В сохранённом OCR первой страницы искажены названия обеих организаций | На первой странице фрагменты надписей, на второй — элемент Image без текста. Названия по такому результату подтвердить нельзя |

Эталон для 70 строк взят из сопутствующих XLSX, включая повторяющиеся артикулы и отображаемое в PDF округление весов. Для инвойса сравнивалось точное мультимножество четырёх значений, для упаковочного листа использовались веса строки, отдельно от веса единицы и итога палеты. Эталонные значения не передавались модели. Одна пара запросов на документ, одинаковая инструкция, профиль `deepseek-flash` с thinking/max, лимит 65 536. Для Unstructured переданы текст элементов и HTML таблиц в порядке выдачи. Дополнительные строки и дубли после модели в обоих вариантах — 0. Простая проверка формата строки измеряет пригодность для чтения кодом, а оценка после модели учитывает и восстановление разнесённых значений.

Это полные токены вызовов по данным провайдера, включая рассуждения. Локальный парсинг Unstructured занял суммарно около 42 с для шести документов, включая инициализацию первого документа, без установки и скачивания весов. Время в таблице относится только к модельным запросам. В изолированной среде зависимости парсера заняли около 1,5 ГБ, два комплекта весов — ещё 317 МиБ по данным du. На основании одного парного прогона нельзя прогнозировать стоимость или задержку всего потока.

### Что изменено в обработчике PDF

На страницах с текстовым слоем Forma ищет отдельную строку с числом. Если pdfplumber находит линованную таблицу, Forma восстанавливает порядок ячеек только при точном совпадении всех слов и чисел с одним уникальным фрагментом исходной страницы. Многострочные ячейки, неоднозначные повторы и плотные чертежи пропускаются. Текст строки заменяется на месте, локатор страницы сохраняется. Версия парсера входит в ключ повторного использования досье. [Обработчик](../agent/src/forma_declaration_agent/documents.py) · [Регрессионные тесты](../agent/tests/test_documents.py) · [Ключ досье](../backend/app/dossiers.py)

Проверены 70 различных по SHA-256 PDF в пяти каталогах примеров, 637 страниц. Для 489 страниц с подходящим текстовым слоем сравнены исходный и новый тексты. Изменилась одна страница упаковочного листа. На ней одно количество вернулось в свою товарную строку, набор слов и чисел сохранился. Остальные 488 текстовых страниц остались идентичны. В пределах полного пятого комплекта повторное чтение всех 12 PDF с тем же пиксельным кэшем OCR также дало одно изменение. Это не охватывает PDF внутри архивов и произвольные документы клиентов.

На банковской ведомости отдельно проверен Tesseract с автоориентацией (`--psm 1`). На первой странице при 300 dpi распознаны полное название нерезидента и номер контракта из повторной надписи. Русскоязычный режим всё ещё удваивает букву в названии резидента. Результата недостаточно для автоматического заполнения сторон. Подходящий следующий контроль — точное название каждой стороны вместе с её ролью, номером и страницей на нескольких повёрнутых и обычных сканах. [Tesseract](https://github.com/tesseract-ocr/tesseract) · [OCRmyPDF](https://github.com/ocrmypdf/OCRmyPDF)

## Три прогона от комплекта до XML

Один и тот же комплект из 12 первичных PDF примера 5 обработан на одном снимке кода, с одной базой знаний, одним профилем модели и одинаковыми правилами заполнения. Первый вариант использовал исходный парсер. Во втором поменялась одна строка упаковочного листа. В третьем заменены результаты чтения четырёх PDF (счёт, упаковочный лист, скан спецификации, банковская ведомость), остальные восемь прочитаны как в контроле. В адаптере Unstructured сохранены имена файлов, номера страниц, текст элементов и строки таблиц из HTML. Страница без текста обработана по тому же правилу пропуска пустого фрагмента, что и в Forma. Для одинаковых запросов переиспользовался кэш. XML специалиста прочитан только после генерации.

| Показатель | Исходная Forma | Forma с чтением по ячейкам | Unstructured для четырёх PDF |
|---|---:|---:|---:|
| Файлов / текстовых фрагментов | 12 / 21 | 12 / 21 | 12 / 20 |
| Товары ДТ / правильные коды ТН ВЭД | 1 / 1 | 1 / 1 | 1 / 1 |
| Совпадения по сопоставимому XML-пути, из 103 | 17 | 17 | 16 |
| Совпавшие графы из 8 отдельно сверенных по первичке | 7 | 7 | 6 |
| Совпавшие сочетания «вид, номер, дата» в графе 44, из 16 уникальных | 1 | 1 | 1 |
| Открытые вопросы / замечания экспорта | 60 / 13 | 60 / 13 | 60 / 12 |

XML исходной Forma и версии с чтением ячеек совпал побайтно. Новое чтение улучшило проверяемость строки в досье. В варианте с Unstructured в XML отсутствовала графа 38, масса нетто. В двух вариантах Forma она содержала подтверждённые 23 686 кг. Эталон примера 5 имеет формат ESADout_CU. Только у 103 из 334 заполненных реквизитов и атрибутов эталона установлено соответствие с AltaGTD; перестановка записей графы 44 влияет на позиционное сравнение. Отдельная строка по графе 44 сравнивает сочетания без учёта порядка. Один прогон каждого варианта не позволяет отделить эффект парсера от вариативности новых модельных ответов. Все три выходных файла — проекты XML; ручной импорт в Альта-ГТД в проверку не входил.

## Два дополнительных испытания на данных Forma

**LangExtract 1.7.2.** Взяты 108 различных подтверждённых троек «документ, локатор, цитата» из базового досье примера 5. Библиотеке дали действительный текст соответствующей страницы и цитату. Её локальный алгоритм привязки, без новой модели, вернул 108 диапазонов символов. В 107 случаях выделенный текст совпал с цитатой после нормализации пробелов и регистра. Затем в 76 цитатах изменили одну цифру и убедились, что изменённого текста на исходной странице нет. Алгоритм по умолчанию всё равно вернул диапазон в 71 случае, пометив его как частичное или нечёткое совпадение. Точная сверка выделенного фрагмента отклонила все 76. Практическое применение — подсветка источника после подтверждения текста. Это испытание привязки цитат с известной страницей. Извлечение новых реквизитов моделью LangExtract отдельно не оценивалось. [LangExtract](https://github.com/google/langextract) · [Проверка цитат Forma](../agent/src/forma_declaration_agent/evidence.py)

**RapidFuzz.** Два английских комплекта IV-14 и IV-15 дали 663 строки упаковочных листов. Для каждой строки правильный артикул известен из XLSX и присутствует в инвойсе того же комплекта. Искомым значением служил напечатанный артикул. Для ранжирования подавались только нормализованные описания, сохраняющие в том числе коды, если они встречались внутри описания. Первый предложенный артикул был верен в 524 из 663 случаев, в первую тройку правильный артикул попал в 576 случаях. Точное совпадение описания давало единственный правильный артикул в 471 случае. Повторяющиеся позиции одного артикула с разными ценами эта проверка не различает. Поэтому похожее название годится для подсказки, а подтверждение конкретной строки требует дополнительных реквизитов. [RapidFuzz](https://github.com/rapidfuzz/RapidFuzz)

## Приоритет для следующей итерации

1. **Графа 44.** У всех трёх вариантов совпало 1 из 16 уникальных сочетаний вида, номера и даты документа в эталоне. Сначала установить, какие записи подтверждаются переданной первичкой и где именно они теряются — при чтении, определении роли, привязке к товару или экспорте. На этом подмножестве сравнивать готовый извлекатель с текущим.
2. **Повёрнутые сканы.** Сравнить текущий OCR с чтением в исходном разрешении и автоориентацией. Проверять точное название, его роль и номер документа. Данный тест нашёл ошибки даже при локально правильном повороте.
3. **Подсказки оператору.** Для подсветки цитат можно использовать диапазоны LangExtract с точной сверкой, для поиска похожих товаров — короткий список RapidFuzz, дополненный артикулом, количеством и единицей. Эти библиотеки испытаны изолированно.

Локальная проверка реализации завершилась 308 тестами агента и 164 тестами backend. Обычный API загрузки и разбора прошли все 104 исходных документа пяти приватных комплектов, включая проверку по сохранённому OCR. Деплой в это испытание не входил.

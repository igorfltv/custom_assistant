# Архитектура

Браузер → публичный Caddy HTTP → gateway → landing / workspace / admin / Python API.
Локальный запуск обращается к gateway напрямую на localhost.
API → PostgreSQL (учётные записи, декларации, профиль, аудит).
API → Redis/RQ → worker → провайдеры OCR и LLM.
API и worker → persistent documents volume.
knowledge-sync → разрешённые публичные URLs → архив снимков, без активации правил.

## Границы ответственности

- Frontend не хранит ключи моделей, не рассчитывает таможенные платежи и не принимает
  решение о юридической полноте декларации.
- Backend авторизует каждую операцию. Админка — отдельная сборка, но доступ
  обеспечивается серверными проверками ролей, а не скрытием кнопок.
- Анализ работает в отдельном процессе. Запуск сохраняет профиль и зашифрованный
  снимок нужных ключей; по завершении/ошибке снимок ключей уничтожается.
- В запросах к модели документы явно помечены как недоверенные данные;
  модель не имеет инструментов для выполнения инструкций из документов.
- Все модельные сведения остаются предложениями до проверки. Ссылка проверяется
  на наличие цитаты в извлечённом тексте, а не на смысловое следование.
- Контекст содержит факты, выводы, неизвестное и конфликты. Неподтверждённый
  «факт» понижается до предположения. Добавление/удаление документа очищает старый контекст.
- Повторный анализ сохраняет ручные поля. Изменения имеют аудит before/after.
- Выпуски анализа сохраняют результат для последующего сравнения.

## Хранение и запуск

Postgres и Redis не публикуют порты. Порт gateway привязан к loopback.
Отдельный Compose-проект Caddy публикует порт 80. HTTPS отключён по решению владельца.
Cookie HttpOnly/SameSite=Strict; COOKIE_SECURE=false для HTTP-прототипа,
проверка Origin у изменяющих запросов, Argon2-пароли, Fernet-ключи провайдеров.
ENCRYPTION_KEY должен сохраняться вместе с резервными копиями, иначе ключи API
невозможно расшифровать. .env и данные не включаются в Git и Docker build context.

Первая версия создаёт схему через SQLAlchemy create_all. Перед первым изменением
схемы уже используемой базы необходимо добавить миграцию; create_all не мигрирует столбцы.
Обновление базовой схемы не должно выполняться удалением volume.

## Что ещё требуется до рабочего XML

1. Подтверждённая XSD и зависимости, namespace и версия целевого формата.
2. Структурированная модель всех реквизитов с условиями применимости.
3. Версионированные классификаторы, тарифы, разрешительные требования, расчёты.
4. Маппинг модели в XML, XSD-валидация, проверки межполей.
5. Эталонные комплекты, содержательная проверка декларантом и ручная проверка файла в Альте.

Итоговый файл выгружается пользователю; модуль загрузки в Альту отсутствует.
